## 1. 测试策略

- **自动化用例（核心逻辑）**：以 Node 运行 `tests/acceptance.test.js`，直接加载 `js/core.js`（UMD），验证 SRS 中全部功能需求的可编程部分。测试内置可注入的固定 `rng`，保证结果确定性、可复现。
- **手动验收清单（浏览器）**：在浏览器打开 `index.html`，逐项勾选 UI / 交互 / 视觉需求。
- 自动化测试命令：`node tests/acceptance.test.js`（需要 Node.js 环境；仅用于开发期验证，不影响最终产品零依赖运行）。

## 2. 自动化用例

### TC-01 棋盘生成与难度参数
- 前置：无。
- 步骤：分别以 初级 / 中级 / 高级 参数创建游戏。
- 断言：
  1. `rows × cols` 与雷数正确（9×9/10、16×16/40、30×16/99）。
  2. 布雷完成后（触发一次首击）棋盘上 `isMine === true` 的格子数恰为 `mines`。
- 对应：FR-01 / FR-02

### TC-02 首击安全
- 前置：创建任意难度游戏，注入固定 rng。
- 步骤：对棋盘上每个可能的首击格 (r, c)（含四角、四边、中央）分别执行首击。
- 断言：首击后，以 (r, c) 为中心的 3×3 邻域内（越界裁剪）无任何 `isMine` 格子。
- 对应：FR-03

### TC-03 邻雷计数正确性
- 前置：固定种子棋盘。
- 步骤：手动构造一个 4×4 已知雷分布的棋盘，调用布雷与计数逻辑。
- 断言：每个格子的 `neighborMines` 与手算值完全一致。
- 对应：FR-04（数字显示基础）

### TC-04 洪泛展开
- 前置：构造已知棋盘：角落 0 区连接大片 0 区，边界为数字 1。
- 步骤：点击 0 区角落格。
- 断言：
  1. 整个 0 连通区全部翻开。
  2. 0 区边界的一圈数字格被翻开。
  3. 数字格之外的格子仍为 hidden。
  4. 洪泛不穿过旗格（在边界放置旗格后重复验证）。
- 对应：FR-05

### TC-05 标记循环与计数
- 前置：新游戏。
- 步骤：对同一格连续 4 次 `toggleMark`。
- 断言：状态依次为 flagged → question → hidden → flagged；期间 `flagCount` 在 flag 进入时 +1、离开时 −1，问号期间不变。
- 对应：FR-06

### TC-06 旗格不可翻开
- 前置：新游戏，首击后。
- 步骤：对某格插旗后调用 `reveal`。
- 断言：该格状态不变，不触发任何翻开。
- 对应：FR-04 / FR-06

### TC-07 Chord 展开
- 前置：构造已知棋盘：数字 1 格周围恰好 1 旗 + 1 hidden 格（hidden 为 0 区）。
- 步骤：对数字格执行 Chord。
- 断言：
  1. 旗数匹配时，周围 hidden/question 格被翻开（含洪泛）。
  2. 旗数不匹配时，无任何变化。
  3. 旗标错（旗下是雷）时 Chord 判负（status === 'lost'）。
- 对应：FR-07

### TC-08 胜负判定
- 前置：构造两种棋盘。
- 步骤 A（胜）：逐格翻开直到最后一块非雷格。
- 断言 A：`status === 'won'`，且计时停止标志被设置。
- 步骤 B（负）：点击雷格。
- 断言 B：`status === 'lost'`；`board` 中所有雷格 `isMine` 可见状态被标记（UI 展示数据齐备：hit 坐标已记录）。
- 对应：FR-08

### TC-09 自定义参数校验
- 前置：无。
- 步骤：对以下输入调用校验函数：`(8,9,10)`、`(41,9,10)`、`(9,8,10)`、`(9,61,10)`、`(9,9,0)`、`(9,9,73)`（超 9×9−9=72 上界）、`(9,9,72)`（恰为合法上界）、`(10,10,20)`（合法）。
- 断言：`(9,9,72)` 与 `(10,10,20)` 通过；其余返回对应中文错误信息（含"行" / "列" / "雷数"关键字段）。
- 对应：FR-02 / FR-13

### TC-10 剩余雷数计算
- 前置：10 雷游戏，首击后。
- 步骤：依次插 3 旗 → 取消 1 旗 → 插 5 旗。
- 断言：`flagCount` 依次为 3 / 2 / 7；剩余雷数 = `10 − flagCount`（UI 侧含负号显示，逻辑侧数值正确）。
- 对应：FR-10

### TC-11 计时接口
- 前置：新游戏。
- 步骤：首击后读取 `timer.startTime`；模拟推进后读取 `getElapsed()`。
- 断言：`getElapsed()` 返回值 ≈ 真实时间差（允许 ±50ms 误差），且与 `setInterval` 无关（纯时间差计算）。
- 对应：FR-09

### TC-12 音效评分数据正确性（FR-14）
- 前置：加载 `js/audio.js`（Node UMD 导出）。
- 步骤：调用 `_getScore('click' | 'flag' | 'win' | 'lose')`。
- 断言：
  1. 四种音效评分均为非空音符数组，每项含 `f / t / d / type / g` 字段。
  2. `win` 音符频率严格递增（上行琶音 C5→E5→G5→C6）。
  3. `lose` 音符起始频率严格递减（下行三连），且末音时长最长（缓慢收尾）。
  4. `click` 时长最短（< 0.1s），增益最低（轻音效不打扰）。

### TC-13 静音逻辑（FR-15）
- 前置：加载 audio.js，注入 mock AudioContext。
- 步骤：`setMuted(true)` → 依次调用 `playClick / playFlag / playWin / playLose`；`setMuted(false)` → 再调用。
- 断言：静音时 mock 上下文未创建任何振荡器；取消静音后各播放函数按评分创建振荡器且**不抛出异常**。

### TC-14 播放健壮性（FR-14 / NFR-01）
- 前置：加载 audio.js。
- 步骤：调用 `_useContext(null)`（模拟无 Web Audio 环境）后调用全部播放函数。
- 断言：全部静默返回，无任何异常抛出。
